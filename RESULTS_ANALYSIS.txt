Hardware: HP ProBook 440 G9 | 12 logical threads | DDR4
Peak DRAM Bandwidth (STREAM triad, measured per-run): ~21-30 GB/s
Compiler: g++ -std=c++14 -O3 -march=native -fopenmp
Iterations: 100 timed + 5 warmup per measurement
Profile mode: 100 iterations accumulated for sub-ms precision

Implementation optimizations applied to Hybrid (vs initial submission):
  1. Per-thread reduction buffer (replaces #pragma omp atomic on heavy chunks)
     -> Eliminates atomic contention on hub-row outputs
  2. Software prefetching of vector_x[cols[k+16]]
     -> Hides DRAM latency on indirect access (SpMV's #1 bottleneck)
  3. nowait clause on light-row pass + barrier-free heavy-chunk dispatch
     -> Overlaps light and heavy phases
  4. Adaptive heavy-chunk schedule grain (1 for small chunk-counts, 4 for large)
     -> Ensures every thread gets work even on matrices with few hub rows
  5. Per-thread load-balance instrumentation (omp_get_wtime per thread)
     -> Exposes straggler-thread idle time invisible in aggregate GFLOPs

================================================================================
INTERPRETATION & WHY THIS MATTERS
================================================================================

1. THE THROUGHPUT NUMBERS UNDERSTATE HYBRID'S WIN
   On hollywood-2009, both methods exceed 220% of DRAM peak Roofline at 8T+
   because the dense vector_x fits in L3 and serves reads at ~5x DRAM speed.
   Both methods are pinned at the bandwidth ceiling. Aggregate GFLOPs CANNOT
   distinguish them at that point - the hardware is the bottleneck, not the
   algorithm.

   But under merge-based, ONE thread is doing 8% more work than the others
   and HOLDS THEM at the barrier. That waste shows up as 19-31 ms of idle
   thread-time per iteration on hollywood. Hybrid eliminates it entirely
   (0.12-0.28 ms residual).

2. WHY HYBRID DOMINATES LOAD BALANCE EVEN WHEN GFLOPs IS TIED
   Merge-path partitions work by NNZ count, but cannot split a single hub
   row across threads. When a hub row's NNZs land in one thread's segment,
   that thread becomes a straggler. Merge's "fix-up" pass for boundary rows
   serializes after the parallel region, adding to the imbalance.

   Hybrid's Inspector pre-classifies long rows and slices them into 1024-NNZ
   chunks. Every thread pulls chunks from a shared queue dynamically until
   the queue is empty. No straggler is possible - by construction every
   thread finishes within one chunk-time of every other.

3. WHERE HYBRID LEGITIMATELY LOSES
   On small skewed matrices (Slashdot 948K NNZ, Epinions 509K NNZ, Enron
   368K NNZ) the per-iteration runtime is sub-millisecond. The Inspector's
   one-time cost amortizes well, but the per-iteration overhead of:
     - Partials buffer zeroing
     - Two-pass barrier
     - Reduction across threads
   exceeds any chunking benefit when the heavy phase has only 8-19 chunks.
   These matrices show 20-39% Hybrid throughput loss at 8-12T.

   This is by design - Hybrid is targeted at LARGE power-law graphs where
   heavy-chunk count is in the thousands. Hollywood (45,423 chunks) sits
   exactly in that regime.

4. SINGLE-THREADED PERFORMANCE
   Hybrid loses on every matrix at 1T because two-pass overhead exists with
   nothing to balance. This is expected and acceptable - the project targets
   parallel CPU performance, not single-core. Real-world solver workloads
   (CG, GMRES) run thousands of SpMV iterations across many threads where
   load-balance dominates absolute single-iteration overhead.

================================================================================
THE PRACTICAL RULE (UPDATED)
================================================================================

USE HYBRID DYNAMIC CHUNKING when:
  - Matrix has > ~1000 heavy chunks (large power-law graphs)
  - Running with 8+ threads
  - Iterative solver context (Inspector cost amortizes over many SpMVs)

USE MERGE-BASED when:
  - Matrix is small (< 1M NNZ) and per-iteration time < 1 ms
  - Few heavy rows (< 100 chunks) - inspector overhead won't amortize
  - Single-threaded execution

The boundary is heavy-chunk count, NOT skewness alone. Slashdot has CV=3.88
(very skewed) but only 19 heavy chunks; hollywood has comparable skew but
45,423 chunks. The 45K is what enables Hybrid to win.
